# 코드 감사 체크리스트

Phase 2에서 사용한다. 7개 분류를 순서대로 점검하되, 프로젝트 성격에 따라 무게를 조절한다
(라이브러리라면 API 일관성에, 서비스라면 보안·성능에, 스크립트 모음이라면 중복·정리에 무게).

## 심각도 기준

| 등급 | 기준 | 예 |
|------|------|-----|
| 🔴 Critical | 데이터 손실, 보안 침해, 주 사용 경로에서의 크래시·오동작이 실제로 발생 가능 | 커밋된 API 키, 사용자 입력이 그대로 SQL/셸에 들어감, 잘못된 계산 결과 저장 |
| 🟠 High | 특정 조건에서 잘못된 동작이나 에러, 방치하면 커지는 문제 | 예외 처리 누락으로 특정 입력에 크래시, 경쟁 조건, 의존성의 알려진 취약점 |
| 🟡 Medium | 동작은 하지만 비효율·혼란·유지보수 비용을 유발 | 죽은 코드, 중복 로직, deprecated API 사용, 불필요하게 무거운 의존성 |
| 🟢 Low | 스타일·일관성·사소한 개선 | 네이밍 불일치, 미사용 임포트, 코드와 어긋난 오래된 주석 |

판단이 서지 않으면 한 단계 낮춰 매기고 "상향 가능"이라고 적는다. 과대평가된 Critical이
하나라도 오탐으로 판명되면 사용자는 리스트 전체를 의심하게 된다.

한 발견이 여러 분류에 걸치면(예: 호출되지 않는 함수가 루프 IO도 갖고 있음) 사용자의
조치가 달라지는 쪽을 주 분류로 삼고(삭제 대상이면 D, 개선 대상이면 E), 겹치는 성격은
상세 블록에 한 줄로 병기한다. 같은 문제를 두 항목으로 만들지 않는다.

## A. 버그·오류

- 예외/에러 처리: 실패할 수 있는 호출(IO, 네트워크, 파싱, 외부 프로세스)이 처리 없이
  방치된 곳. 에러를 잡고 아무것도 안 하는 빈 catch도 포함.
- 경계 조건: 빈 배열/None/null/0/음수/빈 문자열에서 어떻게 되는가.
- 논리 오류: 조건식 방향, off-by-one, 얕은 복사로 인한 의도치 않은 상태 공유.
- 리소스 누수: 파일/커넥션/락이 에러 경로에서도 닫히는가.
- 비동기: await 누락, 경쟁 조건, 처리되지 않은 Promise/Task, 콜백과 async 혼용 사고.
- 타입 경계: 문자열↔숫자 암묵 변환, null/undefined 전파, 날짜·타임존 처리.

## B. 보안

- **시크릿**: 소스와 git 히스토리에 하드코딩된 키·토큰·비밀번호.
  탐지 패턴 예: `api[_-]?key`, `secret`, `token`, `passw(or)?d`, `Bearer `, AWS `AKIA`,
  긴 base64/hex 리터럴. `.env`류 파일이 `.gitignore`에 있는지, 과거에 커밋된 적은 없는지
  (`git log --all --diff-filter=A -- "*.env*"`).
- **주입**: 사용자 입력이 SQL/셸 명령/eval/템플릿에 문자열 조립으로 들어가는 곳.
- 경로 탐색: 사용자 입력으로 파일 경로를 만드는 곳 (`../` 방어 여부).
- 위험한 기본값: 디버그 모드 켜진 채 배포, 전체 바인딩(0.0.0.0), 인증 없는 엔드포인트,
  과도한 CORS.
- **발견한 시크릿 값 자체는 보고서에 옮겨 적지 않는다** — 위치와 종류만 기록한다.

## C. 의존성

읽기 전용 명령만 사용한다. 수정(`audit fix`, 업그레이드)은 Phase 5에서 사용자 지시로만.

- 취약점: 생태계 도구가 있으면 활용 — `npm audit` / `pip-audit`(설치된 경우) /
  `cargo audit` 등. 도구가 없으면 주요 의존성의 버전만 기록하고 "미검사"로 명시.
- 미사용: 매니페스트에 선언됐지만 어디서도 임포트되지 않는 패키지 (grep으로 확인).
- 구버전/deprecated: 메이저 버전이 크게 뒤처졌거나 공식적으로 deprecated된 것.
- 과체중: 일부 기능만 쓰는데 통째로 들어온 무거운 패키지 — 경량 대안이 있으면 메모.

## D. 불필요 코드

- 어디서도 호출되지 않는 함수/클래스/파일. 단, 진입점·동적 호출(리플렉션, 문자열 기반
  라우팅)·설정 파일 참조를 확인한 뒤에 판정한다.
- 주석 처리된 채 방치된 코드 블록.
- 도달 불가능한 분기, 항상 참/거짓인 조건.
- 실험·백업 파일: `old`, `backup`, `copy`, `_v2`, `test2` 같은 이름의 잔재.
- 판정이 애매하면 "사용처를 찾지 못함(동적 참조 가능성 있음)"으로 정직하게 쓴다.

## E. 경량화·성능

- 반복문 안의 반복 계산·IO·쿼리 (N+1 포함).
- 전량 로드 후 일부만 사용: 파일 전체 읽기, `SELECT *`, 전체 목록 fetch 후 첫 항목만 사용.
- 캐시 없이 반복되는 동일한 비싼 연산.
- 배포물 크기: 미사용 에셋, 소스 트리에 포함된 대용량 파일, 중복 리소스.
- 명백한 알고리즘 개선 여지(핫 경로의 O(n²) 등). 핫 경로가 아니면 Medium 이하로.
- 근거 없이 "느릴 것 같다"고 쓰지 않는다. 호출 빈도나 데이터 규모를 근거로 제시한다.

## F. 문서-코드 정합성

- README/CLAUDE.md의 설치·실행 명령이 현재 코드와 맞는가 — 스크립트 이름, 옵션, 경로를
  실제 파일과 대조한다.
- 문서가 설명하는 구조·기능이 실제와 일치하는가 (없는 기능 설명, 이름 바뀐 모듈).
- 주석이 코드와 어긋난 곳 — 동작은 바뀌었는데 주석은 옛날 것.
- 코드에는 있는데 문서에는 없는 필수 설정(환경 변수, 설정 파일 키).

## G. 일관성·구조

- 네이밍·포맷 규칙이 파일/모듈마다 다른가.
- 같은 일을 하는 코드가 여러 구현으로 존재하는가 (통합 후보).
- 계층 위반: 프로젝트가 스스로 정한 구조를 깨는 곳 (예: UI 계층에서 직접 DB 접근).
- 설정 산재: 같은 값(경로, URL, 상수)이 여러 곳에 하드코딩.

## 서브에이전트로 감사할 때

모듈/디렉토리 단위로 나눠 맡기고, 각 서브에이전트 프롬프트에 다음을 포함한다:

- 담당 파일 목록과 **"조사만 하고 절대 수정하지 말 것"** 명시.
- 점검 분류와 심각도 기준 — 이 파일(`references/code-audit.md`)의 경로를 주고 읽게 한다.
- 반환 형식: 발견별로 `{분류, 심각도, 파일:줄, 문제, 근거(코드 몇 줄 인용), 수정안,
  작업량(S/M/L)}`.
- "발견이 없으면 없다고 반환하라. 억지로 채우지 마라."

반환된 결과는 본 세션에서 심각도 기준으로 재검토하고, 중복을 합친 뒤 ID를 부여한다.
서브에이전트가 매긴 심각도를 그대로 믿지 말고 위 기준표로 다시 확인한다.
