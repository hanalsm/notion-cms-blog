# 프로젝트 종합 감사 (Project Audit)

프로젝트 전체를 대상으로 ① 히스토리·구조 전수 조사, ② 코드 감사와 우선순위 수정 리스트,
③ 초보자/전문가 관점 개선 제안, ④ 로드맵 통합을 수행한다. 모든 결과는 파일로 남기고,
코드 수정은 사용자가 항목을 지정한 뒤에만 한다.

## 절대 규칙

이 스킬의 신뢰성은 아래 네 가지에 달려 있다. 다른 지침과 충돌하면 이쪽이 우선한다.

1. **감사 단계(Phase 0~4)에서는 프로젝트 코드를 수정하지 않는다.** 이 스킬은 진단 도구다.
   진단 중에 코드를 고치면 사용자는 무엇이 바뀌었는지 추적할 수 없게 된다. 예외는 두 가지뿐:
   보고서 파일 생성(`docs/audit/`, `ROADMAP.md`)과, 사용자가 확인한 뒤의 로드맵 원본
   아카이브 이동.
2. **모든 지적에는 증거를 붙인다.** 위치(파일:줄)를 직접 확인하지 않은 문제는 리스트에
   넣지 않는다. 실행해 보지 않고 추정한 것이면 "추정"이라고 표기한다. 발견이 적으면 적다고
   보고한다 — 리스트를 채우려고 사소한 것을 부풀리면 사용자가 진짜 문제를 놓치게 된다.
3. **각 Phase가 끝날 때마다 즉시 결과를 파일에 기록한다.** 감사는 길다. 컨텍스트가
   압축되어도 파일에 남은 결과는 유실되지 않고, 사용자는 며칠 뒤 새 세션에서도 이어서
   진행할 수 있다.
4. **감사에 쓰는 모델은 시작 시점의 모델로 고정한다.** 서브에이전트를 포함해, 비용·사용량
   한도·속도 등 어떤 이유로도 모델을 허락 없이 바꾸지 않는다(다운그레이드 절대 금지) —
   감사의 가치는 발견의 품질이고, 품질은 모델 등급에 직결된다. 진행이 막히면(한도 초과 등)
   모델을 바꿔 계속하는 대신 **멈춰서 상황과 선택지를 보고하고 사용자가 결정하게 한다.**
   모델 변경은 사용자가 명시적으로 지시한 경우에만 한다.

## 모드

스킬 인자에 따라 실행 범위를 정한다:

| 인자 | 실행 범위 | 용도 |
|------|-----------|------|
| (없음) | Phase 0→1→2→3→4→5 | 종합 감사 전체 |
| `code` | Phase 0(간이)→2→5 | 코드 감사와 수정 루프만 |
| `improve` | Phase 0(간이)→1(간이)→3 | 개선 제안만 |
| `roadmap` | Phase 0(간이)→4 | 로드맵 통합만 |
| `fix` | Phase 5 | 기존 감사 보고서의 수정 루프 재개 |

"간이"란 해당 Phase에서 다음 Phase의 판단에 필요한 최소한(목적·스택·규모, improve의 경우
git 연혁 훑기 포함)만 수행하고 중간 보고를 생략하는 것.

시작할 때 실행할 Phase들을 TodoList(사용 가능하다면)에 등록하고 진행 상황을 추적한다.

## 출력물

| 파일 | 내용 |
|------|------|
| `docs/audit/AUDIT-<YYYY-MM-DD>.md` | 감사 보고서: 개요·연혁, 발견 사항 리스트(상태 추적), 개선 제안 |
| `ROADMAP.md` (프로젝트 루트) | 총괄 로드맵: 과거 진행 기록 + 향후 계획 |
| `docs/roadmap-archive/` | 통합 후 원본 로드맵 파일 보관 |

보고서는 한국어로 쓴다(코드 식별자·기술 용어는 영어 그대로). 정확한 양식은
`references/templates.md`에 있다 — **보고서를 쓰기 시작하기 전에 반드시 읽는다.**

## Phase 0 — 스코핑

본조사 전에 이 프로젝트가 무엇이고 얼마나 큰지 파악한다. 이후의 모든 판단(조사 전략,
개선 제안의 방향)이 여기서 나온다.

1. **프로젝트 루트 확인**: 현재 디렉토리가 프로젝트 루트인지 확인한다(매니페스트나 `.git`
   존재 여부). 아니라고 판단되면 어느 프로젝트를 감사할지 사용자에게 물어본다.
2. **규모 측정**: 소스 파일 수와 대략적 LOC — 생성물·의존성 폴더(`node_modules`, `dist`,
   `build`, `.venv`, `__pycache__` 등)는 제외. git 저장소면 커밋 수, 첫/마지막 커밋 날짜.
3. **목적 파악**: README, CLAUDE.md, 매니페스트(package.json 등), 최상위 문서를 읽고
   "이 프로젝트는 무엇을 위한 것인가"를 2~3문장으로 정리한다.
   **문서만으로 목적이 불분명하면 추측으로 진행하지 말고 사용자에게 물어본다.**
   목적을 잘못 짚으면 Phase 3의 제안 전부가 과녁을 벗어난다.
4. **조사 전략 결정**:
   - 소스 파일 약 40개 이하: 직접 읽으며 진행한다.
   - 그보다 크면: 모듈/디렉토리 단위로 나눠 Explore(또는 general-purpose) 서브에이전트에
     병렬로 맡기고 결과를 종합한다. 서브에이전트 프롬프트에는 담당 범위, 점검 항목
     (`references/code-audit.md` 경로를 알려준다), 반환 형식, "수정 금지"를 명시한다.
   - 소스 파일 500개 이상: 전수 감사에 시간이 오래 걸림을 알리고, 우선 감사할 영역을
     사용자와 정하거나 전체 진행 동의를 받는다.
5. **보고**: 규모·목적·전략·예상 출력물을 3~5줄로 사용자에게 보고하고 진행한다.
   (간이 모드에서는 1~4만 수행하고 바로 다음 Phase로 간다.)

완료 조건: 목적 요약과 조사 전략이 정해졌고, `docs/audit/` 디렉토리가 준비됨.

## Phase 1 — 전수 조사 (히스토리·구조)

프로젝트의 시작부터 지금까지를 재구성한다. 목표는 "이 프로젝트가 어떤 길을 걸어왔는가"를
처음 보는 사람도 이해할 수 있게 만드는 것.

**git 히스토리** (git 저장소인 경우):

- 전체 커밋 수, 기간, 기여자.
- 주요 마일스톤: 태그, 큰 변경 커밋, 굵직한 기능이 추가된 시점. `git log --oneline
  --reverse`로 흐름을 훑고, 월/분기 단위로 "이 시기에 무엇이 만들어졌나"를 묶는다.
- **핫스팟 분석**: 변경 빈도 상위 10~20개 파일.
  (bash 예: `git log --pretty=format: --name-only | sort | uniq -c | sort -rg | head -20`)
  변경이 잦은 파일은 버그가 몰리는 곳이다 — Phase 2에서 이 파일들을 우선·정밀 감사한다.
- git 저장소가 아니면: 파일 수정 시각과 문서 내용으로 대략의 연대기를 만들고 그 한계를
  보고서에 명시한다. 버전 관리 도입을 Phase 3 제안 후보로 기록해 둔다.

**구조 조사**:

- 디렉토리 구조(2~3단계 깊이)와 각 최상위 디렉토리의 역할.
- 진입점, 핵심 모듈, 모듈 간 의존 방향.
- 문서 인벤토리: 모든 문서 파일(.md 등)을 훑고 분류한다. **로드맵성 문서(로드맵, TODO,
  계획, 마일스톤 등)는 경로를 기록해 둔다 — Phase 4의 입력이 된다.**

완료 조건: 감사 보고서의 "1부. 프로젝트 개요와 연혁" 섹션 작성 완료.

## Phase 2 — 코드 감사

**시작 전에 `references/code-audit.md`를 읽는다.** 7개 점검 분류(버그/보안/의존성/
불필요 코드/경량화·성능/문서-코드 정합성/일관성·구조)와 심각도 기준, 분류별 구체적
탐지 방법이 거기 있다.

- Phase 0에서 정한 전략(직접 또는 서브에이전트 병렬)으로 소스 전체를 커버한다.
  핫스팟 파일은 더 정밀하게 본다.
- 각 발견을 구조화한다: ID(분류문자-번호, 예: B-01), 심각도(🔴🟠🟡🟢), 위치(파일:줄),
  문제, 근거(코드 인용 몇 줄), 수정안, 예상 작업량(S/M/L), 상태(`미처리`로 시작).
- 같은 문제가 여러 곳에서 반복되면 항목을 쪼개지 말고 하나의 항목에 발생 위치를 모은다.
- 분류(또는 모듈) 하나를 마칠 때마다 보고서 "2부. 발견 사항"에 즉시 기록한다.
- 의존성·보안 점검에서 명령을 실행할 때는 읽기 전용 명령만 쓴다. `npm audit`은 되지만
  `npm audit fix`는 안 된다 — 수정은 Phase 5에서 사용자 지시로만.

완료 조건: 요약 테이블 + 항목별 상세 블록이 보고서에 기록되고 심각도별 집계가 나옴.

## Phase 3 — 개선 제안

Phase 0에서 파악한 프로젝트 목적에 비추어, 발전시킬 방향을 두 관점에서 **각각 3개 이상**
제안한다.

- **초보자 관점** = 이 프로젝트를 처음 접하는 사용자/기여자의 눈. 설치·실행 경험, 문서와
  예제, 에러 메시지의 친절함, 흔한 실수를 막는 안전장치, 사용성.
- **전문가 관점** = 숙련 개발자/아키텍트의 눈. 아키텍처와 확장성, 테스트 전략, CI/CD,
  로깅·관측성, 성능 한계, 기술 부채 상환.

각 제안에 포함할 것: 제목 / 무엇을 하는가 / 왜 이 프로젝트에 필요한가(목적·현황과 연결) /
효과(상·중·하) / 난이도(상·중·하) / 첫 단계(당장 시작한다면 무엇부터).

일반론은 금지다. "테스트를 추가하세요"가 아니라 "X 모듈의 Y 로직은 지금 수동으로만 확인
가능한데 이 부분 회귀가 반복됐으니(git 근거) 여기부터 테스트를 붙이는 것이 효과적"처럼,
이 프로젝트의 실제 파일·기능·이력에 닿아 있어야 한다.

완료 조건: 보고서 "3부. 개선 제안" 작성 완료. 사용자가 채택한 제안은 Phase 4에서
로드맵의 향후 계획에 편입한다.

## Phase 4 — 로드맵 통합

**시작 전에 `references/roadmap.md`를 읽는다.** 산재한 로드맵·계획 문서를 하나의 총괄
`ROADMAP.md`로 통합하는 상세 절차가 거기 있다. 골자는:

1. 로드맵성 문서를 전부 찾는다(Phase 1 인벤토리 + 추가 패턴 검색).
2. 각 문서의 항목을 완료/진행중/계획으로 파싱하되, **"완료" 표시를 그대로 믿지 않는다** —
   git 히스토리와 실제 코드로 검증하고 결과를 표기한다. 로드맵 문서는 실제 진행과 자주
   어긋나 있고, 어긋난 기록을 그대로 옮기면 통합본의 신뢰가 무너진다.
3. `ROADMAP.md`를 작성한다: 과거 진행 기록(시간순) + 향후 계획(단기/중기/장기) + 편입 이력.
4. **정지 지점**: 원본 파일들을 옮기기 전에, 어떤 파일을 편입·이동할지 계획을 보여주고
   사용자 확인을 받는다. 확인 후 `docs/roadmap-archive/`로 이동한다. 삭제는 금지.

로드맵 문서가 하나도 없으면: git 연혁과 감사 결과, 채택된 제안으로 첫 `ROADMAP.md`를
만들고 그 사실을 명시한다.

완료 조건: `ROADMAP.md` 생성/갱신, 원본은 사용자 확인 후 아카이브됨.

## Phase 5 — 결과 보고와 수정 루프

**보고**: 채팅에 요약을 제시한다 — 프로젝트 상태 한 줄 평, 심각도별 발견 수, 가장 급한
3~5개, 생성된 파일 경로, 진행 방법 안내("고칠 항목을 번호로 지정해 주세요. 예: B-01, D-03").

**그리고 멈춘다.** Critical이 있어도 먼저 고치지 않는다. 무엇을 어떤 순서로 고칠지는
사용자의 결정이고, 감사 도구가 마음대로 코드를 바꾸면 감사 결과 자체를 신뢰할 수 없게 된다.

**수정 루프** (사용자가 항목을 지정하면, 항목마다):

1. 해당 위치의 코드 현재 상태를 다시 확인한다 — 감사 시점과 달라졌을 수 있다. 문제가
   이미 없어졌다면 그렇게 보고하고 상태만 갱신한다.
2. 수정한다.
3. 검증한다: 프로젝트에 빌드/테스트/린트가 있으면 실행하고, 없으면 최소한 해당 파일이
   문법적으로 유효하고 임포트가 깨지지 않는지 확인한다.
4. 보고서의 해당 항목 상태를 갱신한다: `완료 (YYYY-MM-DD)` / `보류 — 사유` / `무시 — 사유`.
5. 무엇을 어떻게 바꿨는지 보고하고 남은 미처리 항목 수를 알려준다.

- **"전부 고쳐줘"라면**: 심각도 순으로 5개 단위 배치 처리. 배치마다 검증을 수행하고 중간
  보고를 한 뒤 다음 배치로 간다.
- 사용자가 특정 항목에 이의를 제기하면 근거를 다시 확인한다. 지적이 틀렸으면 인정하고
  상태를 `무시 — 오탐`으로 바꾼다.

**fix 모드로 재개할 때**: `docs/audit/`에서 가장 최근 `AUDIT-*.md`를 찾아 미처리 항목을
읽고, 각 항목의 위치를 재확인해 여전히 유효한지 본 뒤, 남은 리스트를 제시하고 루프를
계속한다.

## 컨텍스트 관리

감사는 컨텍스트를 많이 쓴다. 다음을 지키면 큰 프로젝트에서도 끝까지 완주할 수 있다:

- 보고서에 코드 전체를 붙여넣지 않는다 — 증거는 필요한 몇 줄만 인용한다.
- 파일 읽기 물량은 서브에이전트에 맡기고, 본 컨텍스트에는 구조화된 결과만 받는다.
- Phase마다 파일에 기록했다면 이후 판단에 필요한 것은 파일에 다 있다. 긴 세션에서
  앞부분이 흐릿해지면 자신이 쓴 보고서를 다시 읽는다.
